# 治理组：红线、双证据与汇报面板

规则全文在 `AGENTS.md`（Agent 行为纪律节）——读它，本文件只解释为什么。

## 五条红线

1. **绿灯解锁制**：能力只有全绿验证后才可写进文档与汇报。每一条声明都要能回答"验证记录在哪"。组件在库 ≠ 能力可用（metacognition 与回炉第 11 步都是"在库未接线"，只能这么写）。
2. **双证据制**：判断主包真值必须代码精读 + 影子实测双证据。历史教训：只靠 grep 两次误判（tri-path mock 误报为真实、growth-director 误报为带病）。
3. **禁伪勾选**：Roadmap 的 `[x]` 必须真实，发现伪勾选立即改 `[ ]` 附现状。
4. **禁启发式代评分**：门禁分数必须来自真实数据源（KESPI 用库内实体现算），不许自建打分函数模拟——这是 bug 类别，不是实现方式。
5. **阈值唯一来源**：所有阈值在 growth.config.js，组件内不硬编码；环境变量覆盖只在该文件内实现（envNum 模式）。
6. **组件透明化（AGENTS.md 纪律第 8 条，2026-09-04 新增）**：首次向用户介绍 aing、或用户表达"想实现/启用什么功能"时，必须先用**纯文字逐行**展示基本组件清单（名称 + 能给用户做什么 + 状态：已上线/在库未接线/设计中），让用户按需挑选落实范围；不得默认替用户全开，不得只讲上线部分隐去未接线部分。纯文字模板见 `docs/AGENT-ONBOARDING.md` Step 6，状态来源 GREEN-LIST.md。
7. **部署零偏移（AGENTS.md 纪律第 9 条，2026-09-04 新增）**：部署产物=源码，部署机上不改代码、不打补丁。语境区分：本机 yard 的缺陷修复走影子 SOP（维护者内部流程，别写进对下游的要求）；下游 git 克隆部署的缺陷走"源码分支修复 + diff 合回"。语境教训：公开文档里"影子"一词不带说明，下游 agent 读完就想自行搭一套被紧急叫停——公开文档里的机制词汇必须自带语境，或明确标注"维护者侧流程"。

## 汇报面板（强制）

部署/修改完成后，粘贴完整 verify-deploy 报告：

```
✅ C1 Node.js 运行时
✅ C2 依赖三件套
✅ C3 raw/ 知识源
✅ C4 数据库完整性与向量索引
✅ C5 本地语义模型
✅ C6 语义检索冒烟
🟢 ALL GREEN —— 部署验收通过
```

缺失此面板 = 汇报不完整。历史教训：B组自评分 80%→93%→98% 漂移，正是因为自报进度没有机器面板锚定。

## 对外组报告的仲裁姿势

收到的第三方报告（如 B组）先查三样：声明与代码是否矛盾（如"租户隔离"与"写保护"自相矛盾）、是否自造指标、是否踩治理红线（接旁路、写回 config）。仲裁结论只认双证据，报告本身不是证据。
