# SPEC-5.7 · 检索结果按内容去重

> 状态：实装（2026-11-17）
> 上游：SPEC-5.3（双链去重）、SPEC-5.6（后端对照自测暴露的问题）
> 定位：把「同一份知识存了多份」从检索结果里清掉；**不裁定强度加权**（只记录现象）。

---

## 一、问题（实测）

2026-11-17 在真库副本上跑后端对照自测（SPEC-5.6）时暴露：

- 真库 **320 个活跃实体只有 117 种不同内容**——116 组同名同文，最多一组 6 份（`raw/` 与 `wiki-` 之外还有第三、第四份拷贝）。
- SPEC-5.3 的去重只剥 `wiki-` 前缀，对「不同 id、内容一字不差」的重复无效，于是前 3 张卡常常是同一份知识的三份拷贝。
- 后果：不是排序不准，是**槽位被白白吃掉**——判「哪个后端更好」时看到的全是回声。

## 二、行为（spec 即契约）

1. 检索对候选按**内容指纹**去重：`sha1(content)` 相同即视为同一份知识，只留排序最靠前的那条。
2. 既有规则保留：先按 `wiki-` 基名去重（SPEC-5.3 §2.2），再按内容指纹去重；两条规则叠加，先命中者胜。
3. `k` 一律按**去重后**条数计（沿用 SPEC-5.3 的口径）。
4. 只读：去重发生在结果组装阶段，不改库、不删实体、不动 `entity_vectors`。
5. 空内容按指纹处理（两条空内容视为同文，只出一条）；读取异常时退化为旧行为（只按基名去重），不因单条异常炸整体检索。

## 三、强度加权：只记录，不改

- 现状：`score = 相似度 × (0.5 + 0.5 × 强度/9)`，强度 5 → 系数 0.78，强度 9 → 1.0。
- 实测：一条完美匹配（余弦 0.91、强度 5）会被强度 9、余弦 0.88 的条目压过；真库 320 条里强度 5 占 258、8 占 46、9 占 16，足以重排前排。
- 本件**不改**这条公式（属 SPEC-5.3 的既有判据），只把它记进基准文档，供 owner 裁定。冻结集里实体强度全 5，所以评测从没暴露过这件事。

## 四、验收（`test/test-5.7-dedupe-content.js`）

| AC | 断言 |
|---|---|
| AC-1 | 同内容不同 id 的两条实体，检索只出一条 |
| AC-2 | `k` 按去重后计：库里有 3 条同文 + 2 条异文，`k=2` 出 2 条且互不同文 |
| AC-3 | 内容不同、名字相同的两条都保留（不误伤） |
| AC-4 | 双链既有口径不破：`wiki-X` 与 `X` 仍只出一条且优先 raw |
| AC-5 | 只读：跑前后实体 / 向量行数不变 |
| AC-6 | 空内容实体不炸：两条空内容同现时只出其一，检索正常返回 |

## 五、Non-Goals

- 不删重复实体、不合并 id（那是入库侧/去重账的事，另案）。
- 不改强度公式、不改相似度计算、不改后端选择。
- 不改变评测集口径：这是线上检索行为修正，冻结集指标另测。

## 六、依赖

- 上游：`src/vector.js` 的 `search`、`entities.content`。
- 消费者：`retrieval.search` → `predict` / `memo` / 后端对照自测（SPEC-5.6）。
