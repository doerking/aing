# SPEC-6.12 · 落盘安全（原子写 + 单写者锁 + 容量上限）

> v2 的落盘是 sql.js「整库 export → 覆写文件」。这种模式在 proot / 手机上有两个天然敌人：
> **并发多写**（两个进程各持一份内存库互相覆盖）与**写到一半被杀**（半写文件 = 库损坏）。
> proot 杀进程是常态，不是意外。

---

## 一、目标

1. 任何时刻磁盘上的库文件要么是旧的完整版，要么是新的完整版，**不存在半写**。
2. 同一库同一时刻只有一个写者；陈旧锁能自动接管，不永久卡死。
3. 检测外部改写：自己加载之后文件被别人动过，就拒绝覆盖（宁失败不吞数据）。
4. 容量上限：默认 10MB，可 `AING_DB_CAP_BYTES` 调整；超限拒绝写，原库不变。
5. 失败一律回滚到磁盘旧状态，不留下 `tmp`、`lock` 残留。

---

## 二、行为（spec 即契约）

### 2.1 原子落盘

- `export → 写 <db>.tmp.<pid> → fsync → rename 覆盖 <db>`。
- 任一步失败：清理 tmp、释放锁、抛错；磁盘库保持旧内容。
- 成功：无 tmp 残留。

### 2.2 单写者锁

- 锁文件 `<db>.lock`，以 `wx` 独占创建，内容 `{pid, at}`。
- 已存在时先看归属：锁文件 `pid` 对应的进程已死（`signal 0` 探测，EPERM 视为存活）→ 判为死锁，立即删除接管。
- 归属进程存活且未超时（默认 120 秒，`AING_DB_LOCK_STALE_MS` 可调）→ 抛 `db-locked`，不写。
- 已存在但超时，或锁内容不可读 → 按时间阈值删除后接管（陈旧锁不卡死）。
- 锁只在 persist 临界区内持有；失败路径必须释放。

### 2.3 外部改写检测

- 每次成功写入后记录文件 `{mtimeMs, size}`。
- 下次写前比对；不一致 → 抛 `db-stale`（别人动过），不覆盖。

### 2.4 容量上限

- 默认 `10 * 1024 * 1024` 字节，`AING_DB_CAP_BYTES` 覆盖；`AING_DB_CAP_ALLOW=1` 可临时放行。
- 超限 → 抛 `db-over-cap`，**在 rename 之前**判断，原库不变。

### 2.5 正常路径不变

- 常规写入、重开读回与现在一致；`init` 的建表与幂等行为不变。

### 2.6 陈旧 tmp 清理

- `init` 时清扫同目录下 `<db>.tmp.*`。
- 归属 pid 已死 → 孤儿（半写残留），立即删。
- 归属 pid 存活 → 可能是慢写者，只删 mtime 超过锁阈值（默认 120 秒）的。
- 清理尽力而为：失败不阻 init。

### 2.7 崩溃自愈（2026-11-17 补）

- 进程在 persist 任意点被硬杀后，重开必须自动成功，不需要人工删锁/清 tmp。
- 重开后库必须通过 `PRAGMA integrity_check`，既有实体仍在，且能继续写。

## 三、Acceptance Criteria

| # | 判据 | 检验方式 |
|---|---|---|
| AC-1 | 原子写 | rename 抛错 → 原库字节不变、无 tmp 残留 |
| AC-2 | 单写者锁 | 存在活锁 → `db-locked`，文件不变 |
| AC-3 | 陈旧锁接管 | 锁 mtime 超时 → 写入成功、锁被释放 |
| AC-4 | 外部改写 | 加载后外部 touch → `db-stale`，不覆盖 |
| AC-5 | 容量上限 | `AING_DB_CAP_BYTES=100` → `db-over-cap`，文件不变 |
| AC-6 | 正常路径 | 写入后重开读回一致，无 tmp/lock 残留 |
| AC-7 | 陈旧 tmp 清理 | init 后死 pid 孤儿 tmp 消失；活 pid 的 tmp 保留 |
| AC-8 | 死锁/孤儿自动接管 | 锁与 tmp 归属死 pid → init 直接成功，无需人工清理 |
| AC-9 | 硬杀后重开 | 子进程反复写、随机点硬杀 6 轮 → 每轮 init 成功 |
| AC-10 | 硬杀后完整可写 | 每轮重开 `integrity_check=ok`、基准实体在、可继续写 |

---

## 四、Non-Goals

- 不做多进程并发写（单写者就是设计：两个写者本就该排队，不该并存）。
- 不做 WAL / 页级写（sql.js 无此能力，保单文件零原生依赖）。
- 不做加密、不做远端同步。
- 不负责归档与删除（归 SPEC-6.11）。

---

## 五、已知取舍（评估过，不做）

1. **`db-stale` 同秒窗口**：mtime 同秒且 size 不变的外部改动会漏检。判定阈值为 ±1ms，proot/ext4 的 mtime 是纳秒精度，另有单写者锁兜底；实际风险极低，不加密哈希比对（每写一读全库代价不值）。
2. **rename 后目录 `fsync`**：POSIX 崩溃安全理论上要求 rename 后 fsync 父目录。Android ext4 journaling 下 rename 元数据随事务落盘，不额外做；换到无 journal 的文件系统（如某些 USB 盘）时再评估。

---

## 五、契约

- 错误码：`db-locked` / `db-stale` / `db-over-cap` / `db-write-failed`。
- 环境变量：`AING_DB_CAP_BYTES`（默认 10485760）、`AING_DB_CAP_ALLOW`（`1` 放行）、`AING_DB_LOCK_STALE_MS`（默认 120000）。
- 落盘顺序固定：容量判断 → 取锁 → 变更检测 → 写 tmp → fsync → rename → 记 stat → 放锁。
