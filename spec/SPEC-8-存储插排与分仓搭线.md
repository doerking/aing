# SPEC-8 · 存储插排 × 分仓搭线（方向稿）

> 定调（2026-11-17）：**换仓与分仓都排后期，先把方向钉死**。
> 桌面版库太大同样会烦恼，所以要能**调值分仓**；分仓之后靠**搭线 + 预热**把跨仓关联接回来。
> 手机端不变：单库、私有 f2fs、10MB cap。

## 〇 · 三条不变式

1. **上层不认仓**：21 步代谢、检索、装配只依赖插排接口；换仓/分仓不改上层代码。
2. **单文件优先**：每个仓仍是一个 `.db` 文件（原子写 tmp→rename、单写者锁、容量闸照旧，只是闸值按仓配）。
3. **past 只追加**：分仓不得改写原文；实体落在哪个仓是**路由决定**，不是改写。

## 一 · 插排接口（先把缝留好）

```
open(path)           // 开仓
exec(sql)            // DDL / 无结果
query/all/get(sql, params)
run(sql, params)
export() → bytes     // 原子写用
close()
```

- 配置项 `AING_DB_ENGINE=sqljs|node:sqlite|better-sqlite3`（默认 `sqljs`，与当前定量一致）。
- 已落地（2026-11-17）：`src/db-adapter.js` 是全仓唯一 `require('sql.js')` 的模块；`knowledge-store` 与 `migrate` 都经插排开库。
- **剩余缝**：`store._getDb()` 仍被约 60 个组件当作 SQL 入口使用（160 处）。它现在只暴露「已由插排开出的句柄」，换引擎仍能跑（句柄内部实现可换）；但要真正做到「上层不认仓」，后续需逐步把它们改走 `all/get/run`，属分仓时再做。
- 换仓触发点沿用定量文档：库 > 10MB 或 RSS > 150MB 且 search P95 仍达标 → 换 node:sqlite（省堆 6×，查询慢约 11×）。

## 二 · 分仓（可调阈值）

| 项 | 默认 | 说明 |
|---|---|---|
| `AING_SHARD_MAX_BYTES` | 手机 10MB / 桌面 200MB | 单个仓上限；到线即封仓，新料进新仓 |
| 分仓键 | 时间片（`created_at` 月）+ 关键词主域 | 先按时间片切，避免热仓 |
| 路由表 | `shards` 表（仓号、起止时间、主域标签、行数、字节数） | 全局唯一，落在 0 号元仓 |
| 封仓后 | 只读 | 封仓不写；回炉/压缩只能读后重写新仓 |

**为什么按时间片而不是按主题**：作者的知识是**长出来**的，主题会漂；时间片不漂，且与「原始时间」这条铁律同构。

## 三 · 搭线（跨仓关联的替代品）

分仓后，一条边可能跨仓。三种情况：

1. **同仓**：照旧，物理边。
2. **跨仓（强边）**：在 0 号元仓写一条**桥接记录** `bridge(from_shard, to_shard, relation, strength, evidence)`，不复制原文。
3. **跨仓（弱边）**：不落桥，只记关键词→仓号的倒排（见下）。

**搭线索引**（倒排，落在元仓）：
`keyword → [{shard, entities, strength_sum}]`

- 检索时先查倒排 → 得到候选仓 → 只开候选仓（不做全仓扫描）。
- 倒排的更新时机：每轮代谢收口时增量写；封仓后冻结。

## 四 · 预热（冷启动不抖）

手机 proot 醒一次有固定成本（load 库、wasm 堆、跑 21 步），分仓后开仓次数变多，必须预热：

| 预热项 | 做什么 | 何时 |
|---|---|---|
| 仓清单 | 读 `shards` 表 + 各仓 size/mtime | 每次醒 |
| 倒排缓存 | 关键词→仓号表装入内存（只读） | 每次醒 |
| 热门仓句柄 | 最近 N 天访问过的仓先 open | 每次醒 |
| 向量段 | 只对候选仓载向量 | 按需 |

**预热判据**：预热后首查 P95 < 1.5× 稳态 P95，否则回退「只开元仓」。

## 五 · 与双铰链的关系

- **past 分仓、future 留元仓**：future 产物要跨仓对比，留在一处；past 原文按时间片散开。
- 抽库四件（源头/派生/关联/链）跨仓时：源头按仓并行取，链按 `links.created_at` 归并排序（跨仓链走桥接记录时间）。

## 七 · Non-Goals

- 不做分布式/多机同步（正本单点，见项目决定）。
- 不做云端仓。
- 不在本 spec 里改手机 10MB cap（手机端仍单库）。

## 八 · 落地顺序（后期）

1. 插排收口（AC-8.1）——不改行为，只收口子
2. `AING_DB_ENGINE` 切换（AC-8.2）
3. 分仓 + 封仓（AC-8.3/8.4）
4. 搭线倒排 + 预热（AC-8.5/8.6）
5. 跨仓抽库（AC-8.7）

> 判断线：**库没到阈值就不做分仓**。这条 spec 是让将来换仓/分仓不用改上层，不是现在就把库切开。
