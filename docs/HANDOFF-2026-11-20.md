## 三、口径与裁定（这一段新立的）

1. **票面原则**：只有「有人能动手」的维才开工单。
   - `ka` 只能靠**真实访问**抬——引擎造访问＝作弊；它属「该不该退场」的判据（retention/prune），不是工单。
   - `kr` 在场与否由代谢轮自己决定，外部无从接手。
   - `overall` 复合红＝「说不清哪维坏」，只进 memo 读数。
   - 三者仍在 `kespi_scores` 与 `memo.user.proposals` 可见，只是不占名额。
2. **写回原则**：写回不是访问事件。`applyProposalResult` **绝不碰** `last_access` / `status` / `confidence` / `invalid_at` / `strand`。
3. **不越界修**：kd/kc 的修法要靠场域动作（rebond / reconcile）或 P3 候选边过闸，不是「写一段正文」，故只记账（`record-only`）。
4. **判定权不外派**：写回后票留在 `proposed`，由 `verifyTickets` 按 `demand.acceptance` 判——P7 是主权动作。
5. **历史不溯改**：6.55 前落的 ka/kr/overall 单不删，TTL 自然收尾。

## 十、需求真值审计结论（本次最值钱的裁定）

> 只造真需求的机器，不为没观测到的场景加复杂度。

- **O4 围栏：从「假需求」改判为「已观测到触发」**——36 轮并发里拦下一次过期写者。但仍属廉价防御、只在文件库有意义（sql.js 下比的是各自内存副本，拦不住），**不得当收益点宣传**。
- **`busy_timeout` 是必修项**：默认 0 → 另一写者在场直接抛 `database is locked`。已修为 5000ms（AC-b4 钉住）。
- **写者饿死**（sql.js 下输家 0 轮成功，不丢数据但静默做零工作）：**不加重试**——重试引入退避/轮询新面，并发写者本就未被观测到；抛错可被轮状态机记为 `failed`+`last_step`，hook 看得见。
- **`db-stale` 在文件库下不适用**：无整库覆写就没有那个失败模式；防双写靠 `.lock` + 库内 `writer_epoch`。
