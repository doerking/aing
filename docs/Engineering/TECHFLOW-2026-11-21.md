## 二 · 五个决策及其证据链

### 2.1 引擎切换：先量后切，唔拍脑袋

- **问题**：`AING_DB_ENGINE` 默认 `sqljs`（`db-adapter.js`），SPEC-8 修订 A 挂账「负载实测」。
- **读数**（`tools/engine-load.js`，真库副本同负载 2 轮代谢 + 检索查询）：

  | 项 | sqljs | nodesqlite |
  |---|---|---|
  | 峰值 RSS | 295.4 MB | **221.8 MB（-25%）** |
  | 开库 | 70 ms | **7 ms（10x）** |
  | 查询 p50 | 30 ms | 33 ms（持平）|
  | 轮耗时 | 1973 / 1565 ms | 2406 / 1884 ms（sqljs -20%）|
  | 写放大 | 24 次整库覆写 ≈138 MB | **WAL ~4.1 MB（~30x 小）** |

- **判据**：写放大 30 倍差异是决定项——`knowledge.db` 5.75 MB 每轮整库覆写系结构性浪费。
- **拍板**：owner 切 nodesqlite。
- **落地**：`db-adapter.js` 默认值改；SPEC-8 §一 同步。sqljs 专属语义测试强制 `AING_DB_ENGINE=sqljs`（`test-6.12` 测 atomic rename / db-stale），`test-1.1` 与 `tools/sprout-report.js` cleanup 补 `store._close()`（Windows EPERM：node:sqlite 持有文件句柄）。

### 2.2 阈值单源化：唔另起平行表

- **问题**：`0.55/0.45/0.45/0.60` 散落三处硬编码（`field-promote` / `evolution-team` / `self-optimize`）。
- **判据**：仓内已有「离散旋钮单源」（SPEC-3.4，9 旋钮）——扩展佢，唔造第二套。
- **落地**：集中进 `config-runtime.js` `DEFAULTS.kespi`，旋钮 9→13；三组件经 `getKnob` 取值；库内 config 表可覆盖。`C10d` 动态计数自动适应。

### 2.3 阈值校准：声明对账逐位吻合

- **问题**：单源化之后，「呢啲数定得准不准」系唯一能回答「该唔该动」嘅问题。
- **读数**（`tools/kespi-calibrate.js`，真库 322 行）：`overall` p25 0.46 / p50 0.51 / p75 0.62 / p90 0.71。注释声明「真库五维实测 p25 0.46 / p50 0.51 / p90 0.71」——**逐位吻合，差 0**。
- **结论**：阈值为数据校准，非拍脑袋。
- **读数提示**：`geneMin 0.45` 让 **270/322（83.9%）** 过线——低于中位 0.51，闸近乎全开。

### 2.4 geneMin 0.45 → 0.62

- **判据**：83.9% 过线 = 闸唔筛。取 p75 口径 0.62。
- **拍板**：owner 推高至 0.62。
- **落地**：`config-runtime.js` 一处；`test-3.4b` 锁默认值。
- **复核**：实测过线 **103/322（32.0%）**。
- **自我纠错**：先估「约 25% 头部」，工具实测 **32.0%**——估数必验，靠工具纠返。

### 2.5 门禁负载抖动除根

- **症状**：`run-all` 直接跑稳定 167 档 / 1112 断言 / 0 红；`verify-deploy` 全量（33 项并发）时 **C1/C2/C19 一度同红**，子进程报 1107（少 5，恰系新增 `test-3.4b` 断言数）；`VD_ONLY=C19` 隔离跑即绿。
- **根因**：`count-guard.js` 逐档启子进程数 `✅`、C19 parse `run-all` 子进程输出——两者都喺 CPU 争用下抖。
- **拍板**：owner 选「C19 计数对账改 baseline 单源」。
- **落地**：C19 改 `baseline.json` 单源（唔再 parse 子进程输出；现实对账归 C1/C2）+ count-guard 补短档隔离重跑。`test-3.4c-gate-load` 锁。
- **复核**：连跑两轮 verify-deploy 均 33 项 ALL GREEN。
